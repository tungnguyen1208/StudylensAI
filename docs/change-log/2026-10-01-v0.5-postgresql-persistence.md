# Change: PostgreSQL persistence for full-video learning packages

- Code: `2026-10-01-v0.5-postgresql-persistence`
- Date: `2026-10-01`
- Version: `0.5.0`
- Status: `implemented`

## Reason for change

SQLite was sufficient for a local prototype but is not an appropriate runtime
store for concurrent, durable study sessions and background processing jobs.
PostgreSQL is now the ASP.NET Core runtime persistence provider.

## Business behavior: before and after

The Extension, public API and AI contracts remain at 0.5.0. Before this
change, Backend startup opened a local SQLite database. After this change, the
Backend requires a PostgreSQL connection and applies the same full-transcript,
full-video quiz, attempt and history workflow there.

## Architecture decision and rejected alternatives

The existing entities remain canonical to avoid a destructive rename:
`Videos`, `TranscriptCaptures`, `TranscriptCaptureCues`, `QuizAssessments`,
`QuestionAssessments`, `QuestionOptions`, `QuizAttempts`, `AttemptAnswers`,
`StudySessions` and `ProcessingJobs`. Timestamp ranges remain the question
evidence reference because one question can cite more than one transcript cue.
The private `CorrectOptionId` remains the source of truth instead of copying an
`is_correct` flag into every option.

Rejected: a direct SQLite-to-PostgreSQL auto-copy at application startup,
because it could overwrite or silently omit local legacy data; changing public
API contracts solely to rename database tables; and persisting Gemini audio
(the supported fallback is `geminiVideo` over a public URL).

## Affected contracts, data, and modules

- No public API, AI API or extension-message contract changes.
- Backend runtime uses `Npgsql.EntityFrameworkCore.PostgreSQL` and reads
  `ConnectionStrings__DefaultConnection`.
- Provider-neutral migrations produce PostgreSQL native timestamp/boolean
  types. New metadata stores video duration, quiz prompt version/model name,
  and stable question position.
- `LearningPackageWorker` captures update timestamps before `ExecuteUpdate`,
  making startup recovery valid for both SQLite tests and PostgreSQL runtime.

## Compatibility and migration

Existing SQLite files are not deleted or modified. They are legacy/export
data; a future, separately verified export/import task is required before a
team retires one. New PostgreSQL databases apply the complete migration chain.
Development provisioning is supplied by `deploy/docker-compose.postgres.yml`.

## Risks and limits

Docker/PostgreSQL is not installed in the current workstation, so live network
and migration execution against a PostgreSQL server remains an operational
step. The checked-in connection string is intentionally empty; operators must
provide it through environment configuration or a secure secret store.

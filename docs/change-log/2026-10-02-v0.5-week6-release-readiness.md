# Change: Week 6 release readiness

- Code: `2026-10-02-v0.5-week6-release-readiness`
- Date: `2026-10-02`
- Version: `0.5.0`
- Status: `proposed`

## Reason for change

The final project week must turn the current development workflow into a
repeatable local release: a packaged Chrome/Edge Extension, a secured Docker
stack with explicit PostgreSQL migration, release-level end-to-end evidence,
and SRS/SDS documents aligned with the implemented `0.5.0` behavior.

## Business behavior: before and after

Before, developers build the Extension and start PostgreSQL, Backend and AI
Service separately. Browser acceptance and several Week 5 restart/concurrency
cases remain unverified, and the supplied SRS/SDS still describe the removed
interval/segment workflow at contract `0.4.0`.

After, one release workflow builds and verifies the Extension package and
loopback-only Docker stack. Migration runs as an explicit one-shot step, health
checks report readiness without exposing secrets, the remaining failure and
browser cases have evidence, and the existing SRS/SDS describe the implemented
full-transcript, full-video quiz architecture.

## Architecture decision and rejected alternatives

The public business contracts stay at `0.5.0`. The release topology exposes
only ASP.NET Core on host loopback; PostgreSQL and FastAPI remain private to the
Docker network. Database migration is an explicit pre-start job rather than an
unconditional side effect of web-server startup. Extension packaging is an
unsigned deterministic ZIP for local Chrome/Edge sideloading.

Rejected alternatives are exposing PostgreSQL or FastAPI to the host, storing
Gemini or database secrets in images or bundles, changing business contracts
only for operational health endpoints, and creating replacement SRS/SDS files
instead of updating the supplied sources.

## Affected contracts, data, and modules

- No public learning API, AI API or Extension-message shape is planned to
  change.
- Integration HOT files: Extension manifest/build scripts, Backend startup and
  health, AI application wiring, Docker deployment and release scripts.
- Feature acceptance: Dev 1 tab isolation, Dev 2 restart recovery, Dev 3
  concurrent attempt/history recovery, and the Chrome/Edge fault matrix.
- Existing PostgreSQL business data and legacy SQLite artifacts remain intact.

## Compatibility and migration

The Extension, Backend and AI Service remain version `0.5.0`. Existing
PostgreSQL databases apply the same migration chain idempotently. A fresh
database and an upgrade from the previous migration boundary must both pass.
The release process retains the named PostgreSQL volume during ordinary stop
and restart operations.

## Risks and limits

Real Gemini evaluation depends on quota, provider availability and public
YouTube URLs. Chrome/Edge interaction cannot be claimed from automated unit
tests alone. Raw provider logs and local credentials must remain ignored; only
sanitized evidence is committed.

## Acceptance criteria and test evidence

- Extension tests, typecheck, production build, deterministic ZIP and checksum
  verification pass.
- Backend, contract and AI tests pass; fresh/upgrade/restart migration cases
  pass against PostgreSQL.
- Docker release services become healthy with only Backend published on
  `127.0.0.1:5000`.
- Week 5 cases D1-04, D2-04, D3-03, D3-06 and D3-08 plus M-01 through M-08
  have recorded results.
- Three live Gemini smoke cases cover captioned MCQ, captioned short answer and
  public-video transcript fallback.
- SRS/SDS revision `1.2.2` is traceable to contracts, source and evidence and
  passes full-page render review.

## SRS/SDS impact

The supplied documents must remove interval quizzes, delayed session creation
and contract `0.4.0` runtime descriptions. They must describe immediate
sessions, full-video transcript validation/fallback, duration-based question
targets, batch attempts, video-linked history, PostgreSQL, Docker deployment,
retry/idempotency and failure-safe persistence.

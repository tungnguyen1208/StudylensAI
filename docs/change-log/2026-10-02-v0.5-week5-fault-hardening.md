# Change: Week 5 fault hardening

- Code: `2026-10-02-v0.5-week5-fault-hardening`
- Date: `2026-10-02`
- Version: `0.5.0`
- Status: `accepted`

## Reason for change

The Week 5 plan requires the three feature owners to harden the failure paths
that cross browser tabs, video transitions, Backend jobs, AI calls, grading,
evidence review, and history. The prior happy-path implementation did not fully
protect late ON/caption results, concurrent idempotent writes, malformed AI
output, or answer drafts across a failed grading request.

## Business behavior: before and after

Before, a late relay or caption response could race a newer OFF/video state,
some session and retry races could surface database exceptions, and a grading
retry could lose its draft or accidentally reuse one `clientAttemptId` with a
changed payload. Invalid evidence stored outside JavaScript's safe integer
range could also reach the seek boundary.

After, OFF is authoritative across tabs, old video work is cancelled or made
stale, session/transcript/retry races converge through idempotency, AI timeout
and malformed-output failures have explicit retry semantics, and a grading
retry reuses an immutable answer payload with the original
`clientAttemptId`. Invalid evidence is rejected before grading, history, or
player control. History ordering is deterministic and never splits one whole
quiz attempt at the 100-item boundary.

## Architecture decision and rejected alternatives

The existing `0.5.0` feature boundaries and Extension -> Backend -> FastAPI
direction remain unchanged. Reliability is implemented at each owning seam:
browser storage and message origin for Dev 1, durable jobs and database unique
keys for Dev 2, and browser-session attempt state plus atomic Backend writes for
Dev 3.

Rejected alternatives were disabling global ON after a tab failure, generating
a new idempotency key for every retry, accepting partially valid AI quizzes,
persisting partially graded attempts, and trimming history by individual answer
rows when that would split an attempt.

## Affected contracts, data, and modules

- No public request/response shape or contract version changed.
- Dev 1: activation coordination, content-message origin checks, transcript
  cancellation and retry fixtures.
- Dev 2: AI client timeout/error mapping, worker output validation, session and
  retry race handling.
- Dev 3: attempt-session persistence, evidence validation, grading replay, and
  history read ordering.
- Integration HOT files: Side Panel retry routing, service worker and content
  script seek validation. These changes are required to connect the three
  public feature seams safely.

## Compatibility and migration

No database migration is required. Existing attempts remain readable. An older
browser-session draft that lacks `submittedAnswers` is normalized to an empty
submission snapshot and can continue with the same quiz draft. PostgreSQL and
the current `0.5.0` API remain compatible.

## Risks and limits

Automated tests cannot prove Chrome/Edge behavior under real service restarts,
real multi-tab focus changes, or live provider outages. Browser-session draft
state survives Side Panel remounts during the browser session; it is not a
replacement for the Backend as the source of completed attempts. The complete
manual browser matrix remains pending.

## SRS/SDS impact

The final SRS/SDS should state that OFF and video identity are authoritative
gates, retries preserve the same immutable idempotent payload, provider errors
must not create partial quiz/history data, evidence time is a safe non-negative
integer within the player range, and history limits apply to whole attempts.
